# 운영 안내 (수집·배포 안정성)

매시간 GitHub Actions 가 `수집 → 품질 검사 → 배포` 를 실행합니다.
품질 검사에 실패하면 배포를 건너뛰어 **이전 정상 페이지가 그대로 유지**됩니다.

## 1. 소스 상태

`data/status.json` 과 화면 하단 "소스 상태"에 소스별로 표시됩니다.

| 상태 | 화면 표시 | 뜻 | 정상 수집으로 셈 |
|---|---|---|---|
| `ok` | 정상 · N건 | 최근 기사 확보 | ✅ |
| `undated` | 시각 없음 · N건 | 기사는 들어오지만 발행 시각이 없음 (예: 한겨레) | ✅ |
| `stale` | 오래됨 | 가장 최근 기사가 발행 주기 기준보다 오래됨 | ❌ |
| `filtered_all` | 유효 기사 0 | 항목은 있는데 모두 걸러짐 (제목·링크 없음, 언론사 불일치) | ❌ |
| `empty` | 0건 | 피드에 항목이 없음 | ❌ |
| `parse_error` | 파싱 실패 | 응답이 RSS/Atom 이 아님 (오류 페이지 등) | ❌ |
| `http_error` | 요청 실패 | 연결 오류, 4xx/5xx | ❌ |
| `disabled` | 수집 중지 | OPML 에서 `enabled="false"` | 집계 제외 |

단계별 숫자: `http_ok` → `parse_ok` → `entry_count`(피드 항목) → `valid_count`(유효 기사) →
`dated_count`(시각 확인) → `recent_count`(발행 주기 안의 기사), `newest_at`(가장 최근 기사).

**발행 주기**(OPML `cadence`)별 '오래됨' 기준 — `config/quality.json` 의 `cadence_hours`

| cadence | 기준 | 적용 |
|---|---|---|
| `frequent` | 12시간 | 연합뉴스 정치·경제·사회 |
| `daily` | 48시간 | 일반 뉴스 기본값, 전기·에너지 전문지 |
| `weekly` | 21일 | 과학 기본값, Nature·Science·Cell·PNAS·Quanta |
| `monthly` | 45일 | Nature Energy, Nature Electronics, 전기저널 |

**이력**(소스별 `history`): `last_success_at`(마지막 정상 수집), `last_http_ok_at`, `consecutive_failures`
(연속 요청·파싱 실패), `consecutive_empty`(연속 0건), `consecutive_stale`, `problem_since`(문제가 시작된 시각).

## 2. 배포 보류 기준 (`config/quality.json`)

**실패 → 배포하지 않음** (하나라도 해당)

| 항목 | 기준 |
|---|---|
| 정상 소스 | 12곳 미만 **또는** 활성 소스의 40% 미만 |
| 뉴스 기사(36시간 창) | 300건 미만 |
| 국내 후보 사건 | 60건 미만 |
| 해외 후보 사건 | 30건 미만 |
| 주요 뉴스 할당 | 국내·해외 각각 할당의 75% 미만 (국내 18/24, 해외 12/16) |
| 직전 정상본 대비 기사 수 | 60% 넘게 감소 |
| 직전 정상본 대비 국내/해외 후보 | 70% 넘게 감소 |
| 언론사 소재별 정상 비율 | 국내 언론 또는 해외 언론 소스(주요 뉴스용)의 정상 비율 30% 미만 (활성 3곳 이상일 때) |

해외 언론이 모두 실패해도 국내 언론의 국제 기사가 해외 할당을 채워 전체 수치로는 드러나지 않을 수 있어서, 언론사 소재별 비율을 따로 봅니다.

**경고 → 배포는 하고 화면 하단·`health.json` 에 표시**

- 정상 소스 비율 85% 미만, 언론사 소재별 정상 비율 70% 미만, 기사 수 30% 넘게 감소
- 요청·파싱 실패 / 0건 / 오래됨 소스 목록
- 6회 이상 연속 실패한 소스

일부 소스 실패만으로는 배포를 멈추지 않습니다. 2026-11-16 실측은 정상 51/52곳, 기사 약 1,700건,
국내 후보 약 1,050, 해외 후보 약 340 으로 기준과 여유가 큽니다.

**기준값**: 최근 7일 정상 실행이 3회 이상 있으면 항목별 **중앙값**(`data/state/metrics_history.json`)을 씁니다.
한 번의 이상한 실행이 기준을 흔들지 않게 하기 위해서입니다. 없으면 직전 정상 실행(`data/state/last_good.json`) →
배포된 페이지의 `data/health.json` 순으로 찾습니다.
둘 다 없으면 **첫 실행**으로 보고 절대 기준만 검사하며, 결과에 `first_run: true` 로 남깁니다.
첫 실행이 실패하면 배포된 페이지가 아직 없으므로 페이지가 404 로 보입니다. Actions 실행 요약의
"품질 검사" 내용을 확인하세요.

## 3. 갱신 지연 표시 (화면)

- 머리글의 "○○ 업데이트" 와 하단의 "마지막 정상 갱신" 은 배포된 데이터의 생성 시각입니다.
  품질 검사를 통과한 데이터만 배포되므로 이 시각이 곧 마지막 정상 갱신입니다.
- 브라우저가 이 시각과 현재 시각을 비교해 **3시간**(`stale_after_minutes`)이 지나면 노란 "갱신 지연" 안내를 띄웁니다.
  배포가 멈춰도 페이지가 스스로 판단합니다. 페이지를 열어 둔 동안 1분마다 다시 확인합니다.
- **이것은 화면 표시일 뿐 알림이 아닙니다.** 페이지를 열어야만 보입니다. 자동 알림은 아래 5절 설정이 필요합니다.

## 4. 캐시 유실과 복구

아카이브(`data/archive.json`)와 상태(`data/state/`: 사건 ID 대장, 테마 28일 후보, 소스 이력, 품질 기준값)는 GitHub Actions **캐시**에 있습니다.
GitHub 는 7일 동안 쓰지 않은 캐시를 지우고, 용량 한도(저장소당 10GB)를 넘으면 오래된 것부터 지웁니다.

그래서 **스냅샷**을 따로 둡니다.

- 품질 검사를 통과한 실행이 `scripts/state_snapshot.py create` 로 위 파일들과 파일별 sha256 을 담은 `manifest.json` 을 만들어
  Actions artifact `state-snapshot` 으로 올립니다(**30일 보관**). 매일 UTC 0시대 실행, 수동·push 실행, 스냅샷에서 복구한 실행에서 올립니다.
- 캐시가 없으면 워크플로가 만료되지 않은 가장 최근 스냅샷을 내려받아 `state_snapshot.py restore` 로 복구합니다.
  sha256 이 하나라도 맞지 않으면 **아무것도 복구하지 않고** 새로 수집합니다. 캐시에서 이미 온 파일은 덮어쓰지 않습니다.
- 결과는 `news.json` 의 `coverage.restored_from` 에 남습니다: `cache`(캐시) / `snapshot`(스냅샷에서 복구) / `none`(이전 기록 없이 새로 수집).
  화면 하단에도 "스냅샷에서 복구" 또는 "이전 기록 없이 새로 수집" 으로 표시됩니다.

| 경우 | 복구 범위 |
|---|---|
| 캐시 있음 | 전부 |
| 캐시 없음, 스냅샷 있음 | 스냅샷 시점(최대 하루 전)까지의 기사 기록·사건 ID·테마 28일 후보·소스 이력·품질 기준값. 그 뒤 피드에서 빠진 기사만 빠짐 |
| 캐시·스냅샷 모두 없음 | 지금 피드에 남은 기사만. 사건 ID 는 배포된 `news.json` 에서 일부, 소스 이력·기준값은 배포된 `status.json`·`health.json` 에서 복구. 테마 후보는 피드에 남은 범위로 다시 시작하고 화면에 "후보 보관 N일째(재구축 중)" 표시 |

`coverage.archive_started_at` 이 **기록 보관 시작 시각**입니다. 스냅샷에서 복구하면 원래 값이 유지되고, 새로 수집하면 복구 시각으로 바뀝니다.

**복구 경로 시험**: 저장소 Actions → `Update and deploy` → Run workflow 에서 `simulate_cache_loss` 를 켜고 실행하면
캐시를 쓰지 않고 스냅샷 복구 경로로 돕니다. 실행 뒤 사이트 하단 또는 `data/news.json` 의 `coverage.restored_from` 이 `snapshot` 인지 확인합니다.
(2026-11-17 로컬 시험: 실제 데이터 스냅샷 5.9MB 로 빈 디렉터리에서 사건 ID 2,547개 유지, 테마 후보 기간 10.20~ 유지.)

## 5. 예약 실행이 멈췄을 때 (수동 복구)

GitHub 는 **공개 저장소에 60일 동안 활동(커밋 등)이 없으면 예약 실행(schedule)을 자동으로 끕니다.**
보통 며칠 전에 저장소 소유자에게 이메일 경고가 옵니다. 화면에 "갱신 지연" 이 계속 보이면 다음을 확인하세요.

1. 저장소 → **Actions** 탭 → 왼쪽 `Update and deploy` 를 엽니다.
2. 위쪽에 "This scheduled workflow is disabled…" 안내가 있으면 **Enable workflow** 를 누릅니다.
3. **Run workflow** 로 한 번 수동 실행합니다.
4. 실행 결과의 **Summary** 에서 "품질 검사: 통과" 와 배포(deploy) 성공을 확인합니다.
5. 실패했다면 Summary 의 ❌ 항목을 확인합니다. 흔한 원인:
   - 많은 소스가 동시에 실패 → 잠시 뒤 다시 실행 (일시적 장애)
   - 특정 소스가 계속 실패 → `feeds/sources.opml` 에서 해당 줄에 `enabled="false"` 와 `disabled_reason` 을 넣고 커밋
   - Pages 설정이 바뀜 → Settings → Pages → Source 가 **GitHub Actions** 인지 확인

예약 실행이 꺼지지 않게 하려면 60일 안에 한 번이라도 커밋이 있으면 됩니다 (소스 추가·설정 변경 등).

## 6. 외부 감시 (선택, 별도 설정 필요)

화면의 지연 표시는 페이지를 열어야만 보입니다. 갱신이 멈추면 **알림을 받고 싶다면** 아래를 설정하세요.
설정하기 전에는 알림이 오지 않습니다.

**Healthchecks.io (무료 플랜)**

1. https://healthchecks.io 에서 새 Check 를 만듭니다. Period `1 hour`, Grace `2 hours` 권장.
2. 발급된 Ping URL(`https://hc-ping.com/...`)을 복사합니다.
3. 저장소 **Settings → Secrets and variables → Actions → New repository secret**
   - Name: `HEALTHCHECK_URL`, Secret: 복사한 주소
4. 워크플로의 "Ping external monitor" 단계가 성공 시 그 주소로, 실패 시 `주소/fail` 로 신호를 보냅니다.
   신호가 Period+Grace 동안 없거나 실패 신호가 오면 Healthchecks.io 가 이메일로 알려 줍니다.
   예약 실행이 꺼진 경우에도 신호가 끊기므로 알림이 옵니다.

**GitHub 기본 알림**: 워크플로 실패 시 저장소 소유자에게 이메일이 갈 수 있습니다
(GitHub 계정 Settings → Notifications → Actions). 예약 실행이 꺼진 경우에는 실패가 아니라 실행 자체가 없으므로 오지 않습니다.
